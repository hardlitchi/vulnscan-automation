# 設計メモ

## 全体の流れ

```
scope.yaml ──▶ スコープガード ──拒否──▶ 監査ログ / レポート（拒否理由）
                   │許可
                   ▼
        ツールごとに再判定 → nmap / nuclei / ZAP を実行（レート制限付き）
                   │生出力（XML / JSONL / JSON）
                   ▼
        共通 Finding に正規化 → スコープ外 URL の結果を破棄
                   ▼
        SQLite に保存し前回と比較（新規・継続・解消）→ 抑制リスト適用
                   ▼
        Markdown / JSON レポート、Slack 通知、署名付き webhook（任意）
```

## スコープガードの判定順

1. プロファイル名が既知か
2. キルスイッチ（`VULNSCAN_KILL=1` またはファイル）が無効か
3. 対象が承認の `targets`（URL 前方一致 / ドメイン / CIDR）に含まれるか
4. `exclusions` に含まれないか（URL・ホスト名・IP/CIDR）
5. 承認期間内か、実行時間帯内か、プロファイルが許可されているか
6. ホスト名の場合、解決した IP が承認の CIDR 内かつ除外 IP でないか（`verify_dns`）

複数の承認がある場合、すべての条件を満たした最初の承認を採用します。
ツール実行の直前に毎回再判定するため、スキャン中に承認期限切れ・時間帯外・
キルスイッチ有効になった場合は残りのツールを実行しません。

## 指摘の同一性

`sha256(tool, rule_id, target, location)` の先頭 32 文字を fingerprint とします。
証跡（evidence）は実行ごとに揺れるため含めません。

## 解消判定

前回 open だった指摘が今回出なかった場合に「解消」とします。ただし今回正常に
完了したツールの指摘に限ります（ツールが失敗した回に誤って解消扱いしないため）。

## 内蔵 Web アプリ診断（webcheck）

外部ツールに依存しない軽量な Web アプリ診断ランナー（`src/vulnscan/runners/webcheck.py`）。
Python 標準ライブラリ（`urllib`）だけで HTTP GET を行い、OWASP Top 10 相当の確認をします。
nmap / nuclei / ZAP と同じ `Runner` インターフェイスに載るため、スコープガード・再判定・
監査ログ・正規化・差分・抑制はすべて共通で通ります。URL 以外の対象では自動でスキップします。

安全側の既定方針（どのプロファイルでも守る）:

- **読み取り中心**。書き込みや破壊的なペイロードは一切送りません。SQLi の確認も、値に
  シングルクオートを 1 つ足してデータベースのエラー文が反射するかを見るだけの非破壊プローブです。
  反射型 XSS の確認も、スクリプトではない無害なカナリア文字列が本文にそのまま出るかを見るだけです。
- **スコープ内限定**。対象 URL から派生させて叩く URL（機微ファイルのパスや反射確認）は、
  engine が注入する `RunContext.in_scope`（＝ `ScopeGuard.allows_url` と同じ判定）を必ず通し、
  承認スコープ外・除外対象には一切リクエストしません。
- **レート制限**。承認の `rate_limit.rps` に従ってリクエスト間隔をあけます（`_RequestBudget`）。
- **リダイレクトは追わない**。応答ヘッダをそのまま観察し、スコープ外へ出ないためです。
- 本文の読み取りは 512KB まで。接続失敗時も例外を投げず、他ツールの実行を止めません。

プロファイル別の深さ:

| プロファイル | 内容 |
|---|---|
| `passive`  | 対象 URL を 1 回だけ GET。セキュリティヘッダ・Cookie 属性・平文通信・バージョン露出・ディレクトリ一覧・混在コンテンツ・CSRF トークン欠落（受動観察のみ、追加リクエストなし） |
| `standard` | 受動チェック＋少数の安全な GET 探索（機微ファイルの露出・入力の反射・SQL エラーの反射） |
| `active`   | standard をやや広く探索。破壊的検査は含まない |

機微ファイルの露出は、HTTP 200 かつ内容が署名（例: `.git/config` なら `[core]`）に一致した
ときのみ報告し、SPA の index.html が 200 で返るようなケースでの過検知を避けます。

テストは `tests/test_webcheck.py`。`fetch` を差し替えてネットワークを使わずに検証します。

## 署名付き webhook（MeshConsole 連携）

`notify.build_webhook_payload` が対象ごとの未対応（`change`: new / persisting）と解消（fixed）を
まとめ、`notify.post_webhook` が `X-Vulnscan-Signature`（`"<timestamp>.<本文>"` の HMAC-SHA256）を
付けて送ります。受け手は時刻のずれ（MeshConsole は ±5 分）と署名を確かめてから取り込みます。

- 毎回すべての未対応を送る（差分だけでなく状態を送る）ので、受け手が一度取りこぼしても次回で揃います
- `started_at` / `finished_at` と `scanner.source_ips` を送るので、受け手は「診断中に自分の検知が
  反応したか」（検知の自己テスト）と、スキャナを自動ブロックしない設定に使えます
- スキャナは MeshConsole と別のホストで動かす前提です（同じホストだと自分自身を診断することになり、
  送信元 IP での区別もできません）

## スキャナのバージョン固定

`:latest` / `:stable` は診断内容が予告なく変わり、差分の「新規」「解消」が揺れるため、
イメージのタグを固定しています。`VULNSCAN_IMAGE_<NAME>` で一時的に上書きできます。

## Web 画面

- `vulnscan web` で起動する FastAPI アプリ（`src/vulnscan/web/`）。画面から開始した診断も CLI と同じ
  `engine.execute_scan` を通るため、スコープガード・再判定・監査ログ（操作者名つき）は共通です。
- 同時に実行する診断は 1 件まで。進み具合はメモリ上に持ち、結果は SQLite に保存します。
- 自分の PC 以外から開ける設定（`--host` がループバック以外）では Basic 認証のパスワードを必須にし、
  画面からの操作（診断開始・緊急停止）は CSRF トークンで保護しています。
- scope.yaml の編集機能は持たせていません（承認はレビューを経て管理者が行うため）。
